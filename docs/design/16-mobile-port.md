# 1. 背景与目标

## 1.1 背景

《挂机英雄团》当前为 **Web 单页应用（Vue 3 + Go 后端）**，核心玩法是深度策略型文字放置 RPG。游戏设计哲学强调"利用碎片时间进行策略研究"，与移动端的使用场景天然契合，存在明确的移动端移植诉求。

本文件用于：
- 评估将现有游戏移植到移动端的**技术可行性**；
- 明确**障碍清单**与**改造工作量**，为排期提供依据；
- 确定**技术路线**（Web/PWA / 混合壳 / 原生）并说明理由。

## 1.2 目标形态

| 形态 | 目标 |
|------|------|
| 首选 | 移动端 Web（PWA）：手机浏览器可玩、可"添加到主屏幕"、断网可开壳 |
| 备选 | 若后续需要上架应用商店，基于 Capacitor 打包壳，前端代码 100% 复用 |
| 明确排除 | Flutter / RN / 原生重写（收益与成本不成比例） |

# 2. 现状架构盘点

## 2.1 分层视图

| 层 | 技术栈 | 关键事实 |
|---|---|---|
| 后端 | Go + Gin + GORM + SQLite | 单二进制内嵌前端，部署于腾讯云 `119.45.224.68:8080`（**纯 HTTP，无 HTTPS**） |
| 前端 | Vue 3 SPA + Vite（`frontend/`） | 无 PWA / Service Worker / Manifest；`index.html` 已有 viewport meta |
| 战斗 | **双端同源**：前端 `frontend/src/game/combat.js` + 后端 `internal/combat/` | 服务器权威结算，WS 推事件，客户端回放/节流展示 |
| 离线 | 服务器侧战斗循环（`internal/service/combat_loop_service.go`） | 关页/断线后台继续跑，24h 封顶（`offlineCapHours = 24`）；事件落库可重放 |
| 同步 | `frontend/src/game/combatStream.js` | WS 优先（`/combat/ws`），退化 `/combat/events` 轮询兜底 |

## 2.2 关键代码位置

| 关注点 | 位置 | 说明 |
|---|---|---|
| 主战斗界面 | `frontend/src/views/MainScreen.vue`（**10,737 行**，模板 ~2,780 行 + script ~1,780 行 + 样式 ~3,340 行） | 单文件巨石组件，移动端改造核心对象 |
| 战斗区布局 | `MainScreen.vue` `.battle-content` / `.battle-arena` | 桌面双栏/三栏 grid，见 §4.2 |
| 战斗事件流 | `frontend/src/game/combatStream.js` | WS + 轮询双通道、`sortCombatStreamEvents` 事件排序 |

| 离线循环 | `internal/service/combat_loop_service.go` | `offlineCapHours=24`、`clientPresenceTimeout=90s`、tab 隐藏 3s 后 arm offline |

| E2E | `e2e/browser/playwright.config.js` | 当前仅桌面视口 `1920x1080` |
| 部署 | `docs/deployment.md` | 已有 Caddy HTTPS 分步方案（第 169 行起），当前未启用 |

# 3. 有利因素（天然适配移动端）

## 3.1 技术栈即 Web

前端为 Vue 3 SPA，移动浏览器开箱即用；后端 API 与前端完全解耦（REST + WS），**无需重写语言或引擎**。这是最大的成本节约点。

## 3.2 放置玩法与移动端场景契合

离线收益已是**服务器权威结算**：浏览器关闭/切后台后，`combat_loop_service.go` 的调度器继续运行，事件落库，玩家回访时拉取补放。这正是移动端"杀进程/切后台/锁屏"场景所需要的——**无需改造架构，移动端体验天然成立**。

## 3.3 文字 UI 负载极轻

无 3D / 贴图 / 物理引擎，低端机无渲染压力；终端绿风格本身信息密度高，适合小屏阅读。

## 3.4 客户端是"瘦客户端"

战斗模拟、存档、离线结算全部在服务端；客户端只负责展示事件序列。移动网络波动下丢失的是**画面**而非**进度**，容错性远高于客户端权威架构。

## 3.5 已具备的移动端前置条件

- 音频模块已处理 iOS Safari Autoplay 限制（user gesture 内 `resume()`）。
- `combatStream.js` 已具备 WS 失败退化轮询的兜底通道。
- 已有 Playwright E2E 基建，可低成本补充移动视口回归。

# 4. 障碍与改造点

## 4.1 🔴 P0-1 HTTPS（硬性阻塞，上线前置）

- **现状**：公网 IP + 8080 端口纯 HTTP，无域名、无证书。
- **移动端约束**：
  - WebSocket 必须走 `wss://`，即依赖 HTTPS；
  - Service Worker / PWA / 部分浏览器 API（`navigator.storage` 等）要求**安全上下文**；
  - iOS Safari 对非 HTTPS 站点限制最严。
- **方案**：接入域名 + Caddy 反代 TLS（`docs/deployment.md` 第 169 行已有分步方案），后端本身无需改动（WS 地址已按 `window.location.protocol` 自动选择 `ws:`/`wss:`，见 `combatStream.js` `wsBase()`）。
- **预估**：0.5~1 天（含域名解析、证书申请、回归验证）。

## 4.2 🔴 P0-2 巨石组件与桌面级布局（最大工作量）

`MainScreen.vue` 为 10,737 行单文件组件，且布局为桌面设计：

| 布局点 | 现状 | 问题 |
|---|---|---|
| `.battle-content` | `grid-template-columns: minmax(0,1fr) clamp(32rem,42vw,41rem)` | 双栏（战斗区+日志），小屏无空间 |
| `.battle-arena` | `grid-template-columns: minmax(25rem,29rem) minmax(3.5rem,5vw) minmax(17rem,20rem)` | **仅战斗区即 ≥720px**，375~430px 手机必溢出 |
| `.panel` | `width: min(100%, 72rem)` | 面板按桌面宽设计 |
| 负 margin 拉伸 | `width: calc(100% + 4rem); margin: -1.5rem -2rem` | 依赖父容器 padding，破坏小屏流式布局 |

**改造要求**：
1. 拆组件：将日志区、队伍面板、背包、商店、排行榜、统计 Modal、AI 策略编辑器等从 `MainScreen.vue` 抽离（可先按"面板级"拆分，不做过度抽象）；
2. 建立 **375px / 430px 断点**（参考 iPhone SE / iPhone Pro Max 系列），战斗区改**纵向堆叠**：敌人行 → 行动/日志 → 队伍行；
3. 大屏保持现有布局不变，移动端用 media query + 独立布局分支，避免影响已冻结的桌面体验与 E2E 断言。

- **预估**：2~3 周（占总工时一半以上）。

## 4.3 🔴 P0-3 Hover 交互失效

`MainScreen.vue` 中 `:hover` 规则 **35 处**，装备/技能 tooltip、词缀对比悬浮层均为 hover 驱动，触屏无 hover。

**改造要求**：
- tooltip 改为点击/长按展示；
- 检查 tooltip 定位是否被面板 `overflow` 裁剪，小屏下需改为 popover/抽屉式；
- 词缀对比（`.item-compare-columns` 等）在窄屏降级为上下堆叠 + 全屏遮罩。

- **预估**：3~5 天。

## 4.4 🟡 P1-1 网络韧性

移动网络频繁切换、后台挂起导致 WS 断开。现状已有三保险（WS + 轮询兜底 + 事件落库），需补齐：

- WS 断线**指数退避重连**；
- 事件**序号断点续传**（复用 `sortCombatStreamEvents` 的 seq 语义与 `/combat/events` 拉取）；
- `visibilitychange` 前后台切换处理（复用现有 `arm-offline` / `schedule-arm-offline` 逻辑，已针对浏览器关闭场景做过修复，见 git log `5085aa1`、`29399dc`）；
- 弱网下日志批量压缩或降频（现有 `combatPacing.js` 基础上调参）。

- **预估**：2~3 天。

## 4.5 🟡 P1-2 移动端性能

- 战斗日志逐 step 渲染 + 大量响应式绑定，低端机（千元安卓、旧 iPhone）可能卡顿；
- 需在移动视口下 profile，必要时对战斗日志做虚拟滚动；
- 检查动画（血条、浮动反馈、打击脉冲）在低端机的 GPU 占用，可加 `prefers-reduced-motion` 降级。

- **预估**：2~3 天。

## 4.6 🟡 P1-3 触控友好的复杂交互

AI 策略配置（`10-tactics.md`：技能优先级、目标选择、触发条件多级编辑）、技能三选一、装备对比等为桌面鼠标流，触屏下需重做成大按钮 / 分段控件 / 步进式向导。

- **预估**：3~5 天（可与 P0-2 的组件拆分合并推进）。

## 4.7 🟡 P1-4 登录态持久化

token 存 `localStorage`（`frontend/src/game/playerSave.js`），iOS 隐私模式 / 清理缓存即丢失。建议引入 refresh token 或设备绑定，避免玩家"丢档感"。

- **预估**：1~2 天。

## 4.8 🟢 P2 体验打磨

| 项 | 内容 |
|---|---|
| PWA 壳 | Manifest + Service Worker 缓存 SPA 壳，实现"添加到主屏幕"、离线开壳 |
| 安全区 | `viewport-fit=cover` + `env(safe-area-inset-*)` 处理刘海/底部横条；虚拟键盘顶起问题 |
| 字号/触控 | `--font-xs: 0.65rem` 起的小字在低 DPR 屏偏小；触控目标 ≥44px（WCAG） |
| 真机矩阵 | iOS Safari / Chrome / 微信内置浏览器 / 部分安卓 WebView 的兼容验证 |

- **预估**：3~5 天。

# 5. 技术路线决策

## 5.1 选项对比

| 路线 | 成本 | 适用性 | 结论 |
|---|---|---|---|
| **PWA（推荐）** | 中 | 零重写、复用全部 E2E、发版走服务器无需审核；放置游戏重后台结算，对原生能力需求极低 | ✅ 首选 |
| Capacitor 打包壳 | 低-中 | 若需上架应用商店 / 原生推送 / 离线启动体验再升级 | 按需启用 |
| Flutter / RN 重写 | 高 | 需要完全不同的 UI 技术栈 | ❌ 明确不推荐 |

## 5.2 决策依据

1. **服务器权威结算**是放置游戏移动化的最佳形态，客户端仅需"展示"能力，Web 技术栈完全覆盖；
2. 游戏无相机、蓝牙、定位等原生能力诉求，PWA 无功能缺口；
3. 现有 E2E（Playwright）与开发流程（Vite 热更新）全部延续，团队学习成本最低。

## 5.3 后端改动面

后端**几乎不动**：战斗循环、存档、离线结算均已服务器权威；仅需配合 HTTPS 上线（Caddy 层处理，不改 Go 代码）。若后续启用 Capacitor，也无需后端改动。

# 6. 分阶段实施计划

| 阶段 | 内容 | 产出 | 预估 |
|---|---|---|---|
| P0-1 | HTTPS + Caddy + 域名 | 手机浏览器可真实访问，`wss://` 生效 | 0.5~1 天 |
| P0-2 | 拆 `MainScreen.vue`、375/430px 断点、战斗区纵向重排 | 移动端主流程可玩 | 2~3 周 |
| P0-3 | tooltip/词缀对比改触控、复杂交互触屏化 | 移动端全功能可用 | 3~5 天（与 P0-2 并行部分） |
| P1-1 | WS 重连退避、断点续传、前后台处理 | 弱网/切后台不丢事件 | 2~3 天 |
| P1-2 | 移动视口性能 profile、日志虚拟滚动、pacing 调参 | 低端机流畅 | 2~3 天 |
| P1-3 | refresh token / 设备绑定 | 登录态稳定 | 1~2 天 |

## 6.1 建议先行试点

在全面铺开前，先完成 P0-1（HTTPS）打通手机真实访问，再挑 `MainScreen.vue` 中**战斗面板**做单一移动断点试点，验证：
- 战斗区纵向重排效果与性能；
- 触控 tooltip 交互手感；
- E2E 在移动视口下的稳定性。

试点通过后按 §6 阶段表全面推进。

## 6.2 移动端主界面原型（已完成）

为验证 §4.2 的响应式布局方案，已制作静态交互原型：

| 项 | 值 |
|---|---|
| 位置 | `docs/prototype/mobile-main/index.html` |
| 形态 | 单文件静态 HTML（无后端依赖），内置 375/390/430 三档设备宽度切换 |
| 视觉 | 完全复用 [11-ui-tokens.md](./11-ui-tokens.md) 令牌（色值复制自 `style.css` :root），尝试加载项目 Ark Pixel 字体 |
| 数据 | 英雄（瓦里安/吉安娜/安度因）、技能、怪物（迪菲亚强盗/霍格）、地图（艾尔文森林）均取自游戏代码与设计文档，标注为演示值 |
| 预览 | 直接双击打开，或在仓库根目录 `npx serve docs/prototype/mobile-main` |

**原型验证的移动端布局方案**（对应 §4.2 改造要求）：
- 战斗区纵向重排：怪物卡（上）→ 战斗日志（中，滚动主区）→ 队伍卡（下）；
- 桌面 command-deck 改为**底部五 Tab 导航**（战斗/背包/商店/统计/更多），登出/音效/排行榜/版本/留言板收纳至「更多」并分组；

- 日志计算详情行可点击折叠（触屏友好）；日志区保留暂停/继续；
- **v2 视觉收敛**（基于原型评审反馈）：英雄/日志/目标行改用短名（瓦里安/吉安娜/安度因）；日志改「主行+详情行」短行结构，颜色收敛为英雄名(职业色)/技能/伤害/治疗/遭遇五种语义色；移除 Tab 与菜单的 emoji 图标；删除非令牌字号档；统计柱状图改为统一色的 6 柱 SVG 图；
- 375/390/430 三档宽度已通过浏览器实测（无溢出、无控制台错误）。

> 原型仅验证布局与交互范式，非正式实现；后续 P0-2 实施时应以拆分后的 `MainScreen.vue` 子组件取代原型中的模拟数据。

# 7. 验收标准

## 7.1 功能验收（移动视口 375/430px）

- [ ] 注册/登录/存档全流程可用；
- [ ] 战斗展示（战斗区、日志、结算、离线摘要）完整；
- [ ] 队伍管理、装备/背包/商店、技能选择、AI 策略配置全部可触控操作；
- [ ] tooltip 与词缀对比在点击/长按下正常展示且不溢出屏幕。

## 7.2 网络与离线验收

- [ ] 弱网（3G 模拟）下 WS 断开自动重连、事件不丢、步进不重复；
- [ ] 切后台 / 锁屏 / 关闭浏览器后，回访离线收益与在线一致（复用现有结算逻辑）；
- [ ] 飞行模式下可打开 PWA 壳（静态资源已缓存），恢复网络后自动同步。

## 7.3 性能验收（参考机型：iPhone SE 2 代 / 千元安卓）

- [ ] 战斗日志滚动无卡顿（FPS ≥ 30）；
- [ ] 低端机 5 分钟连续战斗无内存显著增长（无泄漏）。

## 7.4 回归验收

- [ ] Playwright 新增 `projects`：`Mobile Chrome (iPhone)` 与 `Mobile Safari` 视口，覆盖注册→战斗→商店→统计主链路；
- [ ] 桌面 1920x1080 既有 E2E 全部保持通过（布局改造不破坏桌面体验）。

# 8. 风险与未决决策

## 8.1 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| `MainScreen.vue` 拆分引入桌面回归 | 高 | 拆分期间保持桌面 E2E 全绿再合入；先"面板级"拆分不重构内部逻辑 |
| 移动端浏览器差异（iOS 文本缩放、键盘顶起、滚动惯性） | 中 | 真机矩阵提前介入（P2），关键交互用 E2E 移动视口覆盖 |
| 低端机性能 | 中 | P1-2 专项 profile；动画走 `prefers-reduced-motion` 降级 |
| 弱网事件乱序/重复 | 中 | 复用已有 seq 排序与轮询兜底；补重连退避测试 |
| 玩家数据安全（token 丢失） | 低 | refresh token / 设备绑定（P1-3） |

## 8.2 未决决策

1. **上线形态**：先"手机浏览器直接访问"还是直接上 PWA（可添加到主屏幕）？——建议先浏览器，PWA 放 P2。
2. **是否上架应用商店**：若确认，需在 P0-2 阶段就按 Capacitor 壳约束规划（如资源路径、安全区），避免后期返工。
3. **移动端交互范式的取舍**：AI 策略配置在触屏上是"完整编辑器"还是"模板+微调"？影响 P0-3 设计，建议试点阶段用真实玩家反馈决定。

# 9. 结论

**技术上完全可行，且架构底子相当好**：
- 服务器权威结算 + 事件落库 + 离线循环是移动端放置游戏的理想形态；
- 没有技术死结；主要成本集中在"桌面向小屏的 UI 重构"（P0-2，约 2~3 周）与"HTTPS 上线前置"（P0-1，约 1 天）；
- 引擎/玩法/后端逻辑均无需移植，后端几乎零改动。

**总工作量约 4~6 周（单人）**。建议按 §6.1 先做 HTTPS + 战斗面板试点，验证后再全面铺开。
